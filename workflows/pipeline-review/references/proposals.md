# Tasks, questions and application

## Task review

Every run reviews dated and undated open Tasks linked to each assessed deal and
Account. Match the actual action and intended outcome, not just the date or subject.
Read the newest message in either direction and any buyer response before deciding
whether the action is still pending. A sent message that completed the action is
not an overdue unsent action; propose completion and a distinct next action if needed.

- Reuse an existing Task only for the same action. Show its ID, subject, exact field
  changes and evidence. Reschedule only to a supported deadline; complete only with
  completion evidence. Do not repurpose a Task for a different action.
- Create only when no suitable Task exists, with verified Contact and Opportunity
  links, subject, due date and mapped status. Refresh open candidates before proposing
  and again immediately before creation. A date-only `task_gap` proves no missing action.
- Limit each approval label to one new Task. If another is needed, present it under
  a separate question with its own option. Never hide extra create fields or provider side effects.
- Ambiguous duplicate closures are questions. Name the kept and closed Task; never
  silently complete a possible duplicate. Incomplete evidence withholds the effect.

## Questions

Keep `Q1`, `Q2` and their options in the reviewed run file. Finish the clear
recommendations, then show one open question at a time using renderer question mode.
Display context, current next steps, evidence, up to three exact options and skip.
An informational option with no changes makes no write. Approval of `Q1-a` applies
only to that displayed option; approval of `all` never includes questions.

A free-text answer that changes an effect becomes a newly displayed option before
anything is written. Keep the old option as superseded and allocate the next unused
suffix, such as `Q1-c`; never overwrite or reuse `Q1-a`. A changed preimage, target,
payload or source-dependent premise invalidates the earlier approval. Only one
alternative of the same question may be approved/applied. Revisions and retries
must account for prior successful fields before presenting any further change.

## Apply

Follow rules#approval and rules#write_protocol. Setup and local rendering checks
cannot authorize a write. Fresh-read the target, retain the exact approved payload,
then record each field result only after independent readback. A returned success
without readback remains unverified. Timed-out creates remain pending until reconciled.

Do not retry successful fields. Retain failed attempts and add the later reconciled
result if a retry is approved and warranted. Render receipts from these outcomes;
missing approved fields remain not attempted. Close with unanswered, skipped,
withheld, partial and failed items named. Keep all run material outside the repo.
